Section 1

Project Overview

Understanding what SpendWiser is, what it does, and the core technologies used.

1.1 What is SpendWiser?

SpendWiser is a full-stack, AI-powered personal finance management application built using the MERN stack (MongoDB, Express, React, Node.js). It helps individuals track their income and expenses, understand their spending patterns through AI-generated insights, connect their bank accounts to receive automatic transactions via SMS parsing, and explore curated investment plans tailored to their financial profile.

The application features a futuristic dark-mode UI with glassmorphism design, animated components, and a "neural/cyber" aesthetic — making finance feel modern and engaging.

💡 Who is this for?
SpendWiser is built for students, working professionals, or anyone who wants a smart, beautiful, and AI-assisted way to understand and control their money — primarily targeting the Indian market (₹ INR currency, Indian investment schemes like PPF, NPS, LIC).

2.3 Data Flow — Step by Step

When User Adds a Transaction

  1. User clicks "Initialize Log" button in the header → TransactionModal opens
  2. User fills in: Amount, Type (Income/Expense), Category, Description, Wallet, Date → clicks "Authorize Protocol"
  3. React addTransaction() is called in App.tsx
  4. UI is optimistically updated immediately (no waiting for server)
  5. An HTTP POST /api/transactions request is sent with JWT Bearer token
  6. Express backend receives the request → JWT middleware verifies token → Joi validates body
  7. If MongoDB is connected → saves to Transaction collection; else falls back to Excel file
  8. Wallet balance is updated locally in React state
  9. Budget spending is auto-recalculated from the new transactions array

When User Clicks "Get AI Suggestions"

  1. User navigates to "AI Advisor" tab → clicks "Get AI Suggestions"
  2. React calls getAISuggestions(transactions) in geminiService.ts
  3. The service calculates: total income, total expenses, savings rate %, category breakdown
  4. This data is sent as a prompt to Google Gemini 2.5 Flash with a JSON response schema
  5. Gemini returns: a summary + 4–6 suggestion cards (saving/investment/warning types)
  6. React renders these as styled suggestion cards with priority badges and impact estimates

Backend – Express API

Every file, every function, every configuration explained.

3.1 Entry Point — server.js

The file backend/server.js is the heart of the backend. It starts the Express application, connects everything together, and begins listening for requests.

What it does, line by line:

  1. require('dotenv').config() — loads all variables from .env file so they are available as process.env.X
  2. Imports Express, CORS, Mongoose, node-cron, path
  3. Imports middleware: apiLimiter (rate limiter)
  4. Imports services: scraperService (investment rates), excelService (Excel file path)
  5. Imports routes for: transactions, auth, bank-details, SMS
  6. Creates the Express app with app.use(express.json()) — allows reading JSON request bodies
  7. Configures CORS: only allows requests from FRONTEND_URL (default: localhost:3001), supports credentials, allows specific HTTP methods and headers
  8. Applies rate limiter to all /api/ routes — max 100 requests per 15 minutes
  9. Calls loadCachedRates() immediately — fills investment rate cache from file/defaults
  10. Schedules a cron job: 0 0 1 */2 * = midnight on the 1st of every 2nd month → runs performScraping()
  11. Runs performScraping() once immediately on server start
  12. Registers a fast endpoint: GET /api/investment-rates/scrape → returns cached rates (no DB needed)
  13. Connects to MongoDB asynchronously at startup; once connected, loads rates from DB
  14. Adds a DB connection middleware for all /api routes — ensures DB is connected before handling requests (with graceful fallback)
  15. Registers all route handlers at their URL prefixes
  16. Registers a global error handler as the last middleware — catches any unhandled errors and returns 500
  17. Starts listening on port 5000 (or process.env.PORT) only if not in production — on Vercel, the serverless function handles this
  18. module.exports = app — exports the app for use in Vercel's serverless entry
// Key startup sequence
loadCachedRates();           // 1. Fill rate cache from file
cron.schedule('0 0 1 */2 *', performScraping);  // 2. Schedule refresh
performScraping();           // 3. Run immediately
connectDB().then(loadRatesFromDB);  // 4. Connect to Mongo + load DB rates

3.2 Database Connection — utils/db.js

This utility manages a singleton MongoDB connection using Mongoose. It prevents opening multiple connections if the server is already connected.

  • connectDB() — checks mongoose.connection.readyState:
    • 1 = already connected → returns existing connection immediately
    • 2 = connecting → awaits the existing promise (no duplicate connections)
    • Otherwise → creates a new connection with mongoose.connect()
  • For localhost/127.0.0.1 URIs, forces IPv4 (family: 4) to avoid DNS resolution issues on Windows
  • Stores the last connection error with lastError so controllers can report it to the client
  • getLastError() — exported function that controllers use to give useful error messages
⚠️ Fallback Mode
If MongoDB is unreachable, the app does NOT crash. Instead, controllers detect readyState !== 1 and fall back to reading/writing the data.xlsx Excel file. This means the app works even without a database!

3.5 Controllers

Auth Controller (controllers/authController.js)

Handles all user account operations:

  • register(req, res) — Creates a new user. Checks for duplicate email, creates User document (password auto-hashed via pre-save hook), sends welcome email asynchronously, returns user data (without password)
  • login(req, res) — Finds user by email (lowercase), calls user.comparePassword() to verify, generates a JWT token with userId and email payload, 7-day expiry, returns { token, user }
  • getUser(req, res) — Fetches user by userId param (JWT protected)
  • updateUser(req, res) — Updates name and/or password (JWT protected). Uses findOneAndUpdate with { new: true } to return updated document
⚠️ All controllers check MongoDB state
Every controller function starts with: if (mongoose.connection.readyState === 1 || readyState === 2). If not connected, it returns a 503 error with the last connection error message. Transaction controller additionally falls back to Excel file operations.

Transaction Controller (controllers/transactionController.js)

  • getTransactions — Finds all transactions, sorted by date descending. Falls back to reading Excel file if no DB
  • createTransaction — Generates UUID, sets defaults (currency='INR'), saves to MongoDB or Excel fallback
  • updateTransaction — Uses findOneAndUpdate({ id }) with body spread + updated timestamp
  • deleteTransaction — Uses findOneAndDelete({ id })
  • clearAllTransactions — Transaction.deleteMany({}) or recreates empty Excel sheet
  • downloadTransactions — Calls res.download(EXCEL_FILE, 'spendwiser-transactions.xlsx')

Bank Controller (controllers/bankController.js)

  • getBankDetails(userId) — BankDetails.findOne({ userId })
  • updateBankDetails — Uses findOneAndUpdate({ userId }, data, { upsert: true, new: true }) — creates OR updates in one query. On first bank save (no existing bank_sync transactions), inserts 4 sample transactions to populate the dashboard with demo data
  • deleteBankDetails(userId) — findOneAndDelete({ userId })

SMS Controller (controllers/smsController.js)

  • receiveWebhook — Accepts { message, from, timestamp } in POST body. Calls parseBankSMS(message) from smsParser.js to extract transaction data. Creates a Transaction document with source: 'sms' and smsFrom: from. Saves to MongoDB or Excel fallback.

3.6 Middleware

JWT Auth Middleware (middleware/auth.js)

Verifies that the request has a valid JWT token:

  1. Reads the Authorization header
  2. Checks it starts with "Bearer "
  3. Extracts the token (everything after "Bearer ")
  4. Calls jwt.verify(token, JWT_SECRET)
  5. If valid: adds decoded payload to req.user and calls next()
  6. If invalid/expired: returns 401 with specific error message

Rate Limiter Middleware (middleware/rateLimiter.js)

Four different rate limiters for different security needs:

LimiterWindowMax RequestsApplied To
apiLimiter15 minutes100All /api/ routes (global)
loginLimiter15 minutes5/api/auth/login only
registerLimiter1 hour3/api/auth/register only
smsLimiter1 hour50/api/sms/webhook

Validation Middleware (middleware/validate.js)

A higher-order function: validateRequest(schema) returns an Express middleware that runs schema.validate(req.body). If validation fails, returns 400 with Joi's error details. If valid, calls next().

3.7 Services

Email Service (services/emailService.js)

  • Creates a Nodemailer transporter using SMTP credentials from environment variables
  • sendWelcomeEmail(userEmail, userName) — sends HTML welcome email after registration
  • Gracefully skips if SMTP_USER or SMTP_PASS are not configured
  • Email template includes the user's name and a welcome message

Scraper Service (services/scraperService.js)

  • Maintains an in-memory cachedRates object with default values for PPF (7.1%), FD (6.5%), NPS (9%), LIC (5.5%), Gold (10.5%), Mutual Funds (14%)
  • loadCachedRates() — reads rates.json file on disk and merges into cache
  • loadRatesFromDB() — queries the Rates MongoDB document and merges into cache
  • performScraping() — uses Axios to fetch ClearTax.in/ppf page, Cheerio to parse HTML, extracts PPF rate with regex. Saves updated rates to file and MongoDB
  • getCachedRates() — returns current cached rates for the API endpoint

Excel Service (services/excelService.js)

  • Uses SheetJS (xlsx library) to manage the data.xlsx file
  • initExcel() — creates the file with headers if it doesn't exist
  • readTransactionsFromExcel() — reads all rows and converts to Transaction objects
  • writeTransactionsToExcel(transactions) — overwrites the sheet with the given array
  • Acts as a complete fallback database when MongoDB is unavailable

3.8 Utilities

SMS Parser (utils/smsParser.js)

A pure function that parses raw bank SMS text using regular expressions — no AI needed:

  • Defines 4 regex patterns to match: "Paid Rs. X", "Debit/Credit of Rs. X from/to BANK", "Amount Rs. X debited/credited", "Rs. X debit/credit"
  • Extracts amount as a float (removes commas from numbers)
  • Determines type by checking for keywords: "paid", "debited", "debit", "sent" → expense; "received", "credited", "credit" → income
  • Extracts merchant/description from "at/from/to [Name]" pattern
  • Detects payment method: GPay, PhonePe, Paytm — appends to description
  • Categorizes based on keywords: food/restaurant/cafe, fuel/petrol/auto, rent/housing, movie/entertainment, shopping/mall, hospital/medical/pharmacy, salary/credited
  • Returns null if no amount pattern matches

3.9 Validators (schemas.js)

Four Joi schemas that validate request bodies before they reach controllers:

  • userSchema: email (valid email, required), password (min 6 chars, required), name (required)
  • transactionSchema: amount (positive number, required), type ('income'|'expense', required), category (required), description (max 500 chars, optional), date (required), walletId (required), currency (default 'INR')
  • bankDetailsSchema: userId (required), accounts array with objects containing bankName, accountNumber, ifscCode, accountType (all required)
  • smsSchema: message (required), from (optional), timestamp (optional)

🔑 Authentication Gate
The very first render check: if (!user) return <LoginPage onLogin={handleLogin} />. If no user is in state, the entire app is replaced with the login page. This is a simple but effective client-side route guard.

4.3 Client Services

Auth Service (services/authService.ts)

A singleton object AuthService with these methods:

  • login(email, password) — POSTs to /api/auth/login. On success: saves JWT token to localStorage['smartspend_token'] and user to localStorage['smartspend_session_v1']. Returns the User object
  • register(email, password, name) — POSTs to /api/auth/register. Saves session to localStorage. Returns User
  • logout() — Removes session and token from localStorage
  • getCurrentUser() — Reads and parses localStorage['smartspend_session_v1']
  • getToken() — Returns the stored JWT token string
  • updateProfile(userId, name?, password?) — PUTs to /api/auth/user/:userId with JWT auth header. Updates localStorage session with new user data

All AI calls go through this service. It initializes the GoogleGenAI client with VITE_GEMINI_API_KEY.

  • suggestions[]: array of AISuggestion objects with: title, description, type ('saving'|'investment'|'warning'), priority ('high'|'medium'|'low'), estimatedImpact (e.g. "Save ₹2,000/month")

Security

How SpendWiser protects user data at every layer.

Security LayerMechanismDetails
Password Storagebcryptjs hashingPasswords are hashed with bcrypt (salt rounds = 10) before storage. Plain passwords NEVER saved.
AuthenticationJWT Bearer TokenLogin returns a signed JWT with 7-day expiry. All protected routes verify this token via middleware.
Rate Limitingexpress-rate-limitGeneral: 100 req/15min. Login: 5 attempts/15min. Register: 3/hour. SMS: 50/hour.

Account MaskingClient-sideBank account numbers shown as ****XXXX (last 4 digits only) in the UI.
Local SessionlocalStorageSession stored client-side only. No server-side session storage reduces attack surface.

⚠️ Known Security Notes for Production
  • The JWT_SECRET defaults to 'your-secret-key' if not set. Always set a strong secret in .env for production.
  • The /api/transactions/download and /api/transactions/data/clear endpoints do not require authentication — they should be protected in a production environment.
  • The Gemini API key is exposed client-side via VITE_GEMINI_API_KEY. For production, consider proxying AI calls through the backend to keep the key server-side.

Section 9

Deployment

How to host SpendWiser on Vercel for free.

Vercel Deployment Architecture

SpendWiser is configured for zero-configuration Vercel deployment using vercel.json: 

{
  "outputDirectory": "client/dist",    // built React app
  "rewrites": [
    { "source": "/api/(.*)", "destination": "/api/index" },  // backend API
    { "source": "/(.*)", "destination": "/index.html" }       // SPA routing
  ]
}

How it works on Vercel:

  1. client/dist — the built React app (Vite output) is served as static files
  2. All /api/* requests are routed to api/index.js which re-exports the Express app as a Vercel Serverless Function
  3. All other routes redirect to index.html — enabling client-side React Router navigation

Deployment Steps:

  1. Push the repository to GitHub
  2. Import project into Vercel Dashboard (vercel.com)
  3. Add Environment Variables in Vercel Settings:
    • MONGODB_URI — MongoDB Atlas connection string
    • VITE_GEMINI_API_KEY — Google Gemini API key
    • JWT_SECRET — Strong random string (e.g., 64 chars)
  4. Deploy — Vercel auto-builds and deploys
⚠️ Important for Vercel Deployment
  • On Vercel, the backend runs as a serverless function — there is no persistent server process. The Excel file fallback (data.xlsx) uses the /tmp directory which is ephemeral (wiped between invocations)
  • You must use MongoDB Atlas (cloud) on Vercel — local MongoDB won't work
  • The scraping cron job won't run on Vercel serverless — you'd need a separate cron service or Vercel Cron features

Local Development Architecture

In development, the frontend (Vite, port 3000/3001) and backend (Express, port 5000) run as separate processes. Vite's dev server proxies /api requests to Express. The root package.json scripts use concurrently to run both simultaneously.

npm run dev   # runs both frontend and backend concurrently
